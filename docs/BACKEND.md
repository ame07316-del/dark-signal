# Backend — سجل الأساس وبداية المرحلة B

> **الحالة الحالية:** خريطة `mansion-ground-v2` مع أبواب مشتركة الحالة المشتركة ٣٢×٣٢ مترًا حلّت محل ساحة collision-test-v1. وصف ساحة ٢٠×٢٠ أدناه تاريخ التنفيذ السابق؛ المرجع الحالي للخريطة هو القسم الأخير و`src/map.ts`.

## النطاق الحالي

خادم غرف وردهة وحركة خادم مع تصادم ساحة اختبار مسطحة. `playing` ليست جولة مكتملة.
توجد واجهة Canvas عربية مع تنبؤ وتصحيح أوليين. المطاردون وWebRTC وجدولة معايرة الفريق لم تُنفّذ بعد.
لا حسابات ولا قاعدة بيانات ولا مسار مالك خاص بعد.

الغرف والجلسات في الذاكرة وتضيع بإعادة التشغيل. اتصال واحد يملك لاعبًا واحدًا؛
رمز العودة عشوائي خاص، لا يُبث للآخرين ويتغيّر عند كل عودة ناجحة.
لا تُسجّل الرسائل أو أسرار الجلسة. يجب ألا يضع العميل token في URL أو سجلاته.

## البروتوكول v1

كل الرسائل JSON نصية، بحد أقصى 1024 بايت. يرسل الخادم `hello` مع `version: 1`.
يمكن إرفاق `requestId` نصي حتى 64 حرفًا؛ يعيده الرد المباشر. ليس مفتاح منع تكرار:
لا توجد إعادة تلقائية للأوامر؛ `start` الثاني يُرفض، و`ready` تعيين قيمة.

| طلب العميل | الحقول | الرد المباشر |
|---|---|---|
| `create` | `name` | `session` |
| `join` | `code`, `name` | `session` |
| `resume` | `code`, `token` | `session` |
| `mic` | `available` boolean، و`threshold` بين 0 و1 عند true | `ack` |
| `ready` | `ready` boolean | `ack` |
| `start` | بلا حقول إضافية | `ack` |
| `leave` | بلا حقول إضافية | `ack` |

مثال: `{"type":"create","name":"سليم","requestId":"1"}`.

`session` يحتوي `code`, `playerId`, `token`؛ احفظه خصوصيًا للعودة.
بعد كل تغيير يُبث `{"type":"room","room":{...}}` وفيه الكود والمضيف والمرحلة
وقائمة اللاعبين (id, name, connected, ready, mic)، دون رموز العودة أو عتبات المايك.
`ack` يحتوي `action` و`requestId` إن وُجد.
`error` يحتوي `code` ثابتًا و`message` عربية و`requestId` إن وُجد.

## السياسات

- ٢–٤ لاعبين؛ الأسماء ١–٢٠ حرفًا/رقمًا مع مسافة أو `_` أو `-`، بلا HTML أو محارف تحكم.
- بدء الجولة للمضيف وحده، مع اتصال واستعداد الجميع وتأكيد المايك والمعايرة.
- بيانات `mic` إقرار من العميل، وليست إثباتًا أن الجهاز يعمل؛ العميل الصوتي الفعلي لاحقًا.
- فصل الشبكة يحفظ المقعد ٣٠ ثانية، ويلغي الاستعداد وحالة المايك؛ العودة تتطلب إعداد المايك من جديد.
- نقل المضيف لأول لاعب متصل عند مغادرته/انقطاعه. لا يستعيده المضيف القديم تلقائيًا.
- `leave` يلغي المقعد ورمز العودة فورًا. تُحذف الغرفة عند زوال آخر مقعد.
- تنظيف المقاعد المنقطعة كل ثانية؛ فحص نبض كل ١٥ ثانية لاكتشاف الاتصالات الميتة.
- حد مبدئي ١٠٠ غرفة و٤٠٠ اتصال للعملية (ليس قياس سعة Render).
- محدد رسائل: ٣٠ رسالة/ثانية مع دفعة ٤٠؛ التجاوز يغلق الاتصال بـ1008.
- تجاوز حجم الرسالة يغلق الاتصال بـ1009؛ العميل البطيء يُفصل عند تراكم أكثر من 64 KiB.
- السماح بالأصول ليس توثيق مستخدم؛ العملاء غير المتصفحين يمكنهم تزوير Origin.
  قبل النشر العام يلزم تقييم تحديد المعدل لكل IP/إنشاء الغرف وحماية الحافة.
- لا كتم/مهلة طرد لانقطاع المايك وحده. يُلغى اتجاه الحركة ويُجمّد اللاعب فور تأكيد انقطاع المايك؛
  مهلة ٣٠ ثانية هنا لانقطاع اتصال WebSocket فقط.

## التحقق

اختبارات حقيقية عبر HTTP وWebSocket بجانب اختبارات منطق الغرف:
السعة والأسماء، المايك والاستعداد، صلاحية المضيف، بدء الجولة، العودة وتدوير الرمز،
تنظيف الغرف، حجب Origin، وحد الرسائل والحجم. لا اختبار أجهزة أو صوت أو Render بعد.

## الحركة — الجزء الثاني من A

بعد بدء الجولة يرسل العميل ٢٠ مرة/ثانية:

```json
{"type":"move","seq":1,"x":1,"z":0,"yaw":0,"mode":"walk"}
```

- `x,z` اتجاه في محاور العالم بين -1 و1، وليس موقعًا؛ العميل يحول اتجاه النظر إلى محاور العالم.
- `yaw` بالراديان بين -π وπ. `mode`: walk/run/crouch بسرعات 2.4/4.8/1.3 متر/ثانية.
- `seq` عدد صحيح آمن غير سالب ومتزايد طوال جلسة اللاعب، بما فيها إعادة الاتصال.
- تُرفض حقول الموقع والسرعة وdt وأي حقول إضافية للحركة؛ الاتجاه القطري يُطبّع لمنع زيادة السرعة.
- لا `ack` مباشر للحركة الناجحة؛ الأخطاء فقط رد مباشر، والنتيجة في بث `state` نحو ١٥ هرتز.
- `state` يحتوي `tick` وقائمة id/x/z/yaw/ackSeq/frozen. `ackSeq` آخر اتجاه طبّقه الخادم،
  وليس عدد خطوات الحركة؛ العميل يعيد وضعه على الحالة المؤكدة ثم يعيد تطبيق
  عينات محلية غير مؤكدة بحد أقصى ٥. هذا تقريب لبروتوكول آخر اتجاه، وليس replay حتميًا.
- آخر اتجاه يحل محل السابق؛ كثرة الرسائل لا تسرّع المحاكاة. يتوقف الاتجاه بعد ٢٥٠ مللي ثانية
  دون تحديث، أو فور انقطاع المايك/الشبكة. الاستعادة لا تعيد تنفيذ الاتجاه القديم.
- الخادم يتقدم ٥٠ مللي ثانية ثابتة لكل callback؛ عند ضغط الخادم تتباطأ المحاكاة بدل قفزة موقع.
- تُرسل `map` بعد كل session، وتتضمن حدود ساحة الاختبار والجدار ونقاط البداية.
  `mapId` في room يحدد النسخة. الساحة ٢٠×٢٠ مترًا، مع جدار داخلي واختبار انزلاق جانبي.
- التصادم أفقي محافظ بمربع نصف عرض 0.3 متر وخطوات صغيرة، بلا قفز أو جاذبية أو سلالم
  أو تصادم بين اللاعبين. ليس خريطة القصر النهائية.
- يبث الخادم كل اللاعبين داخل ساحة الاختبار؛ fog of interest لم يُنفّذ بعد.
- `frozen` يصف انقطاع المايك/الشبكة؛ عدم وجود اتجاه أو انتهاء صلاحيته يوقف الحركة أيضًا.

## العميل المرئي

الصفحة `/` وأصولها المسموح بها فقط تُخدم من خادم اللعبة نفسه، والاتصال يستخدم location.host
مع wss عند HTTPS، بلا localhost في شيفرة المتصفح. البناء يجمع العميل عبر esbuild إلى dist/public.
العميل يشارك دالة التصادم نفسها مع الخادم. نقاط الزملاء تُنعّم بصريًا، وموقع الخادم يظهر كدائرة بيضاء.

الميكروفون عبر getUserMedia مع قياس RMS محلي لخمس ثوانٍ (عتبة أولية = المتوسط + 0.03، بحد 1).
لا رفع أو تسجيل صوت ولا مخرج مكبر صوت. هذه معايرة اختبار فردية فقط؛ جدولة الفريق وإعادة القياس
للتلوث الصوتي طبقًا للتدفق النهائي مؤجّلتان. انقطاع/mute المسار يبلّغ الخادم ويوقف التحكم.
إعادة WebSocket تحاول تلقائيًا العودة بالرمز مع الاحتفاظ بتسلسل الحركة، وتطلب معايرة المايك مجددًا.

التحقق: ١٥ اختبار وحدات/تكامل، واختبار Chromium بمتصفحين منفصلين (عرض موبايل لأحدهما)،
يشمل مايكًا اصطناعيًا ومعايرة واستعداد وبدء وتغير إحداثي مؤكد للحركة ومغادرة، بلا أخطاء JS.
لم تُختبر أجهزة أو شبكات أو مايكات حقيقية بعد، ولا يُعد اجتياز محاكاة الموبايل ضمان أداء هاتف.

## بداية B — عرض منظور أول

`client/view3d.ts` يبني مشهد Three.js من ARENA نفسه: حدود وأرضية وجدار داخلي، بلا تغيير خريطة
التصادم أو تحميل أصول. موضع الكاميرا من حركة اللاعب المتوقعة بارتفاع 1.65 م (1.1 عند التسلل بصريًا).
الاتجاهات تُحوّل من فضاء الكاميرا لمحاور العالم ثم تُطبّع قبل الإرسال؛ `yaw` يبقى ضمن ±π.
النظر بالماوس المقفول أو بالسحب، مع دعم pointer capture للمس والنظر المنفصل عن أزرار الحركة.
النظر لا يعمل قبل جاهزية المايك/عند الانقطاع. الكشاف SpotLight محلي واحد، بلا ظلال ديناميكية،
مع ضباب وتقليل pixel ratio إلى 1.5 بحد أقصى؛ لا ادعاء تحقيق 30FPS على هاتف حقيقي قبل قياسه.
عند تعذر WebGL تُعرض رسالة ويبقى الوضع العلوي؛ عند فقد السياق تُعرض رسالة للعودة للخريطة.
الأشكال المؤقتة والمواد المسطحة ليست اعتمادًا فنيًا أو قصرًا نهائيًا.

الاختبارات أصبحت ١٧ وحدة/تكامل واختبار متصفحين واحد يختبر أيضًا تبديل 3D والكشاف وF
وحركة أمامية مؤكدة من الخادم والسحب في عرض موبايل ثم الرجوع للخريطة بلا أخطاء JS.

## مخطط القصر الأولي — B، الجزء الثاني (الحالة الحالية)

- المصدر `src/map.ts`؛ يعاد تصدير ARENA من movement للحفاظ على توافق الواردات.

  ممر غربي وآخر شرقي، وثلاث غرف في كل جناح. المطبخ والمخزن غربًا والاستقبال والمكتب شرقًا.
- جميع الفتحات دائمة حاليًا؛ ليست أبوابًا مقفلة أو تفاعلية. الغرف الإضافية علامات blockout غير نهائية.
- العرض يبني كل الجدران من مصفوفة التصادم؛ أسقف خارج الفناء فقط. الأرضية لا تتغير رأسيًا،
  ولا يوجد قبو أو سلالم أو طابق علوي بعد؛ هذا جزء من المكان في القصة وليس القصر الكامل.

- العميل يتحقق من map.id عند استلام map؛ اختلافه يعطّل الحركة والاستعداد ويطلب تحديث الصفحة.
- ٢٠ اختبار وحدة/تكامل ناجحة، تشمل صلاحية مجسمات الجدران وتباعد نقاط البداية، بحث مسارات
  لكل منطقة مسماة ثم إعادة المرور الفعلي عبر advance، والمرور من فتحة الفناء ومنع عبور جوارها.
  اختبار المتصفحين بالعرضين العلوي والثلاثي ما زال ناجحًا. لم يُختبر هاتف أو شبكة حقيقية.

**الخطوة التالية:** أبواب تفاعلية أولية بسلطة الخادم مع اختبارات المسافة وحالة التصادم، قبل الألغاز والأصول النهائية.

## الأبواب — B، الجزء الثالث (الحالة الحالية)

- نسخة الخريطة `mansion-ground-v2`. تعريفات أربعة أبواب في ARENA.doors؛ كل غرفة تملك
  سجل doors مستقلًا، true مفتوح وfalse مغلق. كلها تبدأ مفتوحة.
- طلب العميل: `{"type":"door","id":"entry-west","open":false}`، مع requestId اختياري.
  هذا تعيين صريح قابل للتكرار بلا عكس للحالة، وليس toggle على الخادم.
- الرد ack/action=door ثم room يحتوي doors؛ بث state يحتوي doors أيضًا، بما في ذلك العودة.
- الخادم يتحقق من اللعب والاتصال والمايك، ومعرّف الباب وboolean، ومسافة مركز الفتحة ≤1.8م،
  ومسار خالٍ من الجدران والأبواب الأخرى. تغيير فعلي واحد لكل لاعب كل 500ms (ضبط أولي).
- أخطاء متخصصة: INVALID_DOOR، TOO_FAR، DOOR_OBSTRUCTED، DOOR_COOLDOWN، DOOR_OCCUPIED.
- الإغلاق يرفض تداخل أي لاعب مع مساحة الباب الموسعة بنصف عرض اللاعب 0.3م، حتى المنقطع
  والمجمد. منع احتجاز لاعب داخل مجسم أولى من السماح بالإغلاق وقت انقطاعه.
- الأبواب المغلقة تُضاف إلى التصادم في محاكاة الخادم، والتنبؤ والمصالحة يستخدمان آخر حالة مؤكدة.
  العميل لا يتنبأ بتغيير حالة الباب قبل التأكيد. العرض العلوي يميز الفتح بالأخضر والإغلاق بالذهبي،
  و3D يظهر جسمًا خشبي اللون عند الإغلاق ويخفيه عند الفتح، بدون حركة باب نهائية.
- لا مفاتيح أو ألغاز أو أصوات أبواب أو AI يسمعها حتى الآن.
- ٢٤ اختبار وحدة/تكامل، واختبار متصفحين يقترب من باب ويغلقه ويتحقق أن z لا يتجاوز الجدار،
  ثم يفتحه ويمر عبره. typecheck والبناء ناجحان؛ اختبارات الأجهزة الحقيقية ما زالت غير منفذة.

**التالي:** بداية C بمنطق مطاردين على الخادم ومسارات دورية ومطاردة أولية، قبل نظام الإمساك والقلوب الكامل.

## المطاردان — بداية C (الحالة الحالية)

  لا هدفًا داخليًا أو مسارًا أو آخر موقع معروف. عند العودة تُرسل الحالة فورًا.

  دون أسرار الهدف ومنع الإغلاق على مطارد. اختبار المتصفحين السابق يثبت أيضًا وصول حالتي المطاردين للواجهة.
- لا اختبار تحميل غرف متزامنة أو 30FPS هاتف أو أجهزة حقيقية؛ الحدود المبدئية ليست ضمان سعة.

**التالي:** الإمساك على الخادم مع القلوب والسقوط والإحياء/الفرصة الأخيرة، وفق User Flow المعتمد.

## وضع تجربة فردية (طلب المالك)

create يقبل mode اختياريًا: coop (الافتراضي) أو solo-test؛ أي قيمة أخرى تُرفض بـINVALID_MODE.
room يحتوي mode، ويستخدمه الخادم لتحديد الحد الأدنى للبدء: ٢ للتعاون و١ للتجربة.
غرف solo-test ترفض join بـSOLO_ROOM حتى في الردهة، ويظل resume متاحًا بنفس الرمز ومدة العودة.
المايك والمعايرة والاستعداد وكل قواعد الحركة والأبواب والمطاردين لم تتغير. لا لاعب وهمي أو صلاحية مالك.
الواجهة تضيف زر إنشاء منفصلًا، وتعرض تعليمات الاستعداد المناسبة، دون تخفيف شروط الغرف التعاونية.
التحقق: ٣٤ اختبار وحدة/تكامل واختبارا متصفح ناجحان؛ الاختبار الفردي ينشئ غرفة بلاعب واحد،
يعاير مايكًا اصطناعيًا ويبدأ ويعرض 3D ويتحرك ويغادر. لم يُختبر مايك جهاز حقيقي.

## تنفيذ الصوت — الحالة الحالية

- الوحدات: src/audio.ts لطابور المعايرة وسياسات الصوت والتحقق من الإشارات؛ client/sound.ts للمؤثرات؛ client/voice.ts لنقل WebRTC. التفاصيل والتقدم في AUDIO_TASKS.md، والاختبار الحقيقي في AUDIO_TEST_CHECKLIST.md.
- AudioContext واحد لكل جلسة جهاز، يفتحه المستخدم؛ المؤثرات فقط لها gain قابل للتعديل. المايك المحلي متصل بمحلل RMS فقط وليس بالسماعة، ونفس المسار يُستخدم لكل زميل. كل الأصوات مولدة محليًا بلا أصول مدفوعة أو طلبات CDN.
- `calibrate` يعلن جاهزية جهاز الصوت voiceAvailable ويضع اللاعب في طابور، لكن لا يجعله Ready أو mic معتمدًا. voiceAvailable يسمح باستمرار المحادثة أثناء القياس، منفصلًا عن الاعتماد للعب.
- `calibration` يحمل active {playerId,startedAt,attempt,quiet} وqueue. `calibration-result` من العميل يتضمن threshold [0,1] وcontaminated boolean؛ يتحقق الخادم من دور اللاعب ومرور 5 ثوانٍ ومهلة 20 ثانية. إعادة واحدة ثم قبول بتحذير. العتبة RMS الخلفية×2 (+6dB تقريبًا)، بحد أدنى .003. لا ادعاء كشف مثالي لتلوث القياس.
- طلب mic:true قبل اكتمال المعايرة يُرفض؛ mic:false يلغي الطابور ويوقف الحركة دون طرد. المعايرة في الواجهة تأخذ نحو 5.1ث بعد وصول الدور لتجنب انتهاء قياس قبل مدة الخادم.
- `level` {level:[0,1]} أربع مرات/ث؛ تحقق خادم ومهلة قبول 200ms. فوق العتبة يولد إشارة ضوضاء بموقع الخادم وقوة محدودة. downed/spectator لا يجذبان AI، لكن كل اللاعبين الحاليين active لعدم تنفيذ نظام الحياة بعد.
- خطوات من الإزاحة الفعلية: كل 1.1م مشي/.85م جري/1.4م تسلل بقوى .5/1/.15 (قيم ضبط أولية)، وأبواب مؤكدة فقط. outbox للأصوات bounded ولا سجل إعادة أحداث؛ sounds كل 250ms، بمعرّف حدث لمنع التكرار على العميل.
- `signal` {to,data}: وصف data={kind:offer|answer,sdp} حتى 12KiB، أو kind:ice مع candidate حتى 2048 حرفًا وsdpMid/sdpMLineIndex مقيدين. غرفة واحدة ومخاطَب غير الذات فقط؛ SDP/ICE لا يُسجّلان. حد نقل WebSocket 16KiB لكن أي رسالة غير signal تظل ≤1KiB. إشارات: burst40/refill10ث، بجانب حد الاتصال العام 30ث/burst40.
- voice-policy كل 250ms: weights للاستقبال وoutgoing للإرسال، لكل مصدر/وجهة. في الردهة صوت عالمي للمتصلين بأجهزة جاهزة، وفي اللعب قرب خطي 8م ومعامل جدار/باب .55. مصدر spectator عالمي؛ سياساته مجهزة لا يمكن للعميل اختيار دوره.
- RTCPeerConnection لكل زميل (ست وصلات كحد أقصى) عبر STUN فقط. offerer بتحديد ثابت من playerId، وتخزين ICE المبكر حتى 128 عنصرًا. الصوت غير المرغوب مكانيًا يُمنع باستبدال track:null على المرسل وليس بإيقاف جهاز القياس؛ gain المستقبِل يعود بسلاسة.
- فقد الجهاز أو فشل/تعذر وصلة بعد 18ث، أو انقطاعها المستمر 8ث، يوقف جهاز المايك محليًا ويبلغ الخادم لتجميد اللاعب وحده. إعادة المحاولة بإعادة تشغيل المايك والمعايرة؛ لا مهلة طرد لانقطاع الصوت وحده. إعادة WebSocket تطلب الجهاز من جديد حفاظًا على وضوح الإذن.
- صوت RTP مشفر بين المتصفحات بواسطة WebRTC، لا يمر خامًا بخادم اللعبة ولا يُسجل. يستخدم STUN لتبادل عناوين الاتصال؛ قد يرى الزملاء عناوين الشبكة، وخادم STUN طرف خارجي. لا TURN ولا ضمان لشبكات المؤسسات/CGNAT.
- ٤٢ اختبار وحدة/تكامل و٣ اختبارات Chromium ناجحة: مرور بايتات RTP، فصل إرسال البعيد ثم رجوعه، وقف الحركة بفقد الجهاز وإعادة معايرته، أربع جلسات بست وصلات، ومعايرة/مؤثرات/حماية الغرف. لا ادعاء جودة سمعية أو جهاز هاتف حقيقي أو شبكتين حقيقيتين.

**المتبقي من خطة الصوت:** ربط الدور downed/spectator عندما يتوفر نظام الحياة/الهروب، وتجارب الأجهزة والشبكات الفعلية وضبط المزيج بحسب ملاحظات المالك. لا تُعتبر هاتان الجزئيتان منجزتين.
